# Vector

This is the data ingest pipeline for the platform. [Vector](https://vector.dev)
reads messages from the MQTT broker, reshapes them, and writes them into
GreptimeDB (our time-series database). It is the bridge between "a device
published something" and "you can query it in Greptime".

Vector runs as the `vector` service in `docker-compose.yml` (part of the
`data-collection` profile) and as a Helm release in the cluster. Both use the
same `config.yaml` and `processing/` files from this directory.

## How data flows

Vector's config has three parts: **sources** (where messages come from),
**transforms** (how they are reshaped), and **sinks** (where they go). We run
three separate pipelines through it:

### 1. General MQTT → GreptimeDB

The main pipeline. It subscribes to the everyday topics (`marpower/#`,
`domestic/+`, `hull-temperature/...`, `termodinamica/#`, `sail-systems/#`,
`power-tags/#`), then runs each message through six steps in `processing/`:

| Step | File | What it does |
|------|------|--------------|
| 0 | `0_consts.vrl` | Lookup tables that map a topic to its Greptime table name. **Auto-generated** by `zero-data`. |
| 1 | `1_table.vrl` | Picks the table name for this message from those lookups. |
| 2 | `2_flatten.vrl` | Flattens nested JSON into flat `a__b` keys. |
| 3 | `3_timestamp.vrl` | Finds the newest `*TimeStamp` field, or falls back to "now". |
| 4 | `4_spell_fix.vrl` | Normalises `TimeStamp` → `Timestamp` in key names. |
| 5 | `5_snakecase.vrl` | Converts all keys from `PascalCase` to `snake_case`. |

The result lands in a per-domain table via the `greptimedb` sink.

### 2. A+T (ATPX) instrument bus → `atpx_raw`

A+T's onboard instrument bus publishes one raw number per message on a topic
like `atpx/<field-id>/<source>`. This pipeline (`atpx_parse` transform) turns
each message into one row: it looks up the human-readable field name and sender
name (`atpx_0_consts.vrl`, also **auto-generated** by `zero-data`), then writes
`{topic, sender, field, value}` into a single `atpx_raw` table. A pivot view
builds the wide, per-domain shapes later.

It also republishes each parsed row back onto our own broker under
`atpx/processed/<field>/<sender>` for other consumers.

The topic it listens on is `${ATPX_MQTT_TOPIC}`. Locally that is `atpx_raw/#`
(so synthetic test data stays separate); in production the variable is unset and
defaults to A+T's real `atpx/#` bus.

### 3. A+T NMEA 0183 → `atpx__nmea_*`

A+T also emits NMEA 0183 sentences. The standalone `zero-atpx-nmea` service
parses those into JSON and republishes them on `atpx/processed/nmea/<type>/<sender>`.
This pipeline (`atpx_nmea_route.vrl`) just reads the sentence `type`, derives the
table name `atpx__nmea_<type>`, and writes one row per sentence.

## Directory layout

```
config.yaml              Vector's main config: sources, transforms, sinks.
processing/              The VRL transform steps (see the tables above).
  0_consts.vrl           AUTO-GENERATED by zero-data (marpower/general lookups).
  atpx_0_consts.vrl      AUTO-GENERATED by zero-data (ATPX field + sender names).
  *.vrl                  Hand-written transform steps.
templates/               Helm templates that mount config.yaml + processing/ as ConfigMaps.
Chart.yaml               Helm chart metadata.
tests/                   Golden-file test cases and expected output.
test*.sh                 Test runner scripts (see AGENTS.md).
```

> **Auto-generated files:** `0_consts.vrl` and `atpx_0_consts.vrl` are written by
> `zero-data` (see `zero-data/src/zero_data/vector_gen/`). Do not edit them by
> hand — regenerate them from `zero-data` instead.

## Running it locally

Vector needs the broker and Greptime to talk to. The easiest way to bring up the
whole ingest path, including the synthetic ATPX data generator, is:

```bash
docker compose up --build vector data-gen
```

Via `depends_on` this also starts `vernemq` (broker), `greptimedb`, and
`zero-atpx-nmea` — nothing else. `data-gen` publishes synthetic ATPX, Marpower,
and SailSystem traffic in the real message shapes, so the full path can be
exercised end-to-end without any real hardware.

Key environment variables (set in `docker-compose.yml`):

| Variable | Local default | Purpose |
|----------|---------------|---------|
| `MQTT_HOST` / `MQTT_PORT` | `vernemq` / `1883` | Main broker. |
| `ATPX_MQTT_HOST` / `ATPX_MQTT_PORT` | `vernemq` / `1883` | ATPX broker (real bus is `10.1.40.10` in prod). |
| `ATPX_MQTT_TOPIC` | `atpx_raw/#` | ATPX topic filter; unset in prod → `atpx/#`. |
| `GREPTIMEDB_HOST` / `GREPTIMEDB_PORT` | `greptimedb` / `4000` | Where rows are written. |
